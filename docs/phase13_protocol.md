# MemoryLab Phase 13 — Human-reviewed answer-support challenge

**Purpose:** Test whether the lightweight Phase 12 lexical novelty screen flags genuinely unsupported answers while allowing valid paraphrases, **without adapting the screen to the new case labels first**. The case set contains 32 new fictional source/answer pairs. Every candidate answer is a project-authored test string, **not a response generated by Qwen**.

## Step-by-step on Windows

1. GitHub Desktop: **Fetch origin → Pull origin**.
2. Open your normal MemoryLab terminal (activate your `.venv` if needed). Run the offline regression tests:

```bat
python -m unittest discover -s tests -v
```

**Expected: 253 tests.** The new source and tests have been committed, but execution on your Windows machine is not yet confirmed.

3. Launch the dedicated review screen:

```bat
python -m streamlit run app_answer_challenge.py
```

4. For each of the **32** fictional cases, read the retrieved memory facts, the question, and the proposed answer. Judge whether the **complete answer** is `supported`, `unsupported`, or `uncertain`. Unsupported includes claims that are false, obsolete, not established, incorrectly attributed, or that contradict the available facts. Uncertain means you genuinely cannot determine whether to accept the candidate answer; add an explanation. The screen does **not** show the lexical probe's flags or predictions.

5. Select **Save review** for each item. Edits before freezing are recorded in the local audit. When all cases have a saved judgement, confirm your attestation and click **Freeze all 32 reviews**. Frozen labels cannot be edited through this tool.

6. Run the detector evaluation *only after freezing*:

```bat
python -m scripts.evaluate_answer_challenge
```

7. Open `results/raw/phase13_probe_evaluation.md` to see **false negatives** (unsupported answers that the probe failed to flag), **false positives** (supported answers unnecessarily flagged), and a per-case breakdown. Upload the report here for diagnosis. The matching JSON report contains the individual reviewer labels and detector outputs.

## Data integrity and privacy

- Benchmark: `benchmarks/answer_claims_v1.json` in the repository, with **no gold labels or probe scores embedded**.
- Labels: `results/raw/phase13_answer_signoff.json` in your Git-ignored private results folder, with a source SHA-256 and append-only audit events until freeze.
- Evaluation: `results/raw/phase13_probe_evaluation.md` and `.json`. Both refuse to overwrite previous results.
- These programs **do not call Ollama**, do not read the private `memorylab.db`, and never change Phase 10–12 source files or historical reviewed decisions.
- If the dataset changes, its hash no longer matches the saved labels and the evaluation refuses to proceed. Do not manually edit the case source after labelling.

## Scientific limits

The source cases and candidate answers were crafted in the project to stress suspected weaknesses. The reviewer is blind to the probe's outputs, **not** to the candidate answer. A single review does not establish independently sourced factual ground truth, and detector precision/recall on curated cases must not be extrapolated to real traffic or Qwen model accuracy. Human reviewers can also disagree about ambiguous claims. The challenge is a reproducible **development stress test**, not a blind external benchmark.

**Never auto-block real user answers or memory updates solely because the novelty probe flags a token.** Preserve the existing live answer generator and human confirmation workflow.

See [Experiment 019](experiment_019_results.md) for findings and scope.
